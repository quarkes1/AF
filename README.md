全部有效界面参考图、立绘及样式说明集中在规格书第 23 章。后续开发必须同时遵守相应图版、交互说明、工程结构与验收契约。

AF 必须自包含交付：用户只安装 AF，无需另装 dsh、Node.js、Python、Office／LibreOffice 或 MCP 宿主。完整包包含核心本地运行依赖；在线模型仍需 API key，可选平台功能需账号授权。交付范围和干净机器验收见规格书 25.2.1。

共享接口与状态机按 17.11、25.2.2、25.3.1 实施；草稿与角色会话隔离按 25.4.1。先完成 F15 契约，再按 20.8 的明确依赖开发；核心回归、候选包、干净机器实测和最终验收依次执行。21.4 的 CT01–CT18 固定用例是后续验收依据，文档检查通过不表示应用功能已实现或通过实测。

`assets/` 保存正式运行素材，`docs/assets/` 保存规格书引用的参考图和数学示例。六张 Aurore 全身立绘及清单位于 `assets/characters/aurore/`，透明矢量标志位于 `assets/brand/`。

工程目录以规格书第 17.12 节为准：`src/`、`tests/`、`scripts/`、`config/` 为后续实现预留，`build/` 与 `tmp/` 用于可重建产物和临时文件。旧实现与历史交付文件已从当前工作目录清除，历史通过 Git 查询。变更按规格书第 22 节执行，不并列维护另一份有效规格。

`scripts/docs/` 为本地文档辅助目录，受 `.gitignore` 忽略，不随仓库分发，也不构成应用实现。文档维护后同步唯一 Markdown 规格源与同版本 PDF，检查资源引用、任务依赖并渲染核对版面；中间页图及临时脚本留在本地忽略目录，不提交或推送。

文档校验须拒绝含糊前置、编号范围、未知／重复任务、依赖环、核心闭包遗漏及参考表误改，不能把正则没有匹配到的前置当成空依赖；这些检查不代替应用的 CT01–CT18 实测。正式交付文件范围和提交前检查见 `Agent.md` 第 7 节。
